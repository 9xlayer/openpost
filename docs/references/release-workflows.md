# Release workflow comparison

Reviewed on 2026-10-26 to repair OpenPost's release feedback loop. The objective is local typechecks and relevant tests before push/tag, fast local fixes, and separately reported remote validation, publication and deployment. Five-minute preparation remains a measured target, not permission to omit a suite.

## What was wrong in OpenPost

At `87c214421`, `ship` ran release metadata checks locally, then pushed and waited for full main CI before tagging. It never invoked the advertised local `check` command. This made GitHub the first place to discover many ordinary code failures. Main concurrency could cancel the selected revision, and a resumed invocation refused an older candidate after main advanced. The watcher treated every canceled run as a newer main push and omitted the canceled job's log.

The prior release also spent almost 25 minutes installing FFmpeg before backend tests hit their job deadline. Another attempt spent approximately 13 minutes installing Playwright system dependencies. These are setup delays, not evidence that tests themselves need that time. The incident and exact run links are recorded in [issue 473](https://github.com/getopenpost/openpost/issues/473).

Local measurement found additional problems:

- The existing `release check` stopped after 401.68 seconds, before its lint and principal test phase. Reachability analysis needed mobile dependencies that this command had not installed, although CI installed them.
- Its public-route policy took 203.70 seconds because a production regression forced marketing and docs builds twice. The same file also belonged to the repository test sweep, so a later phase could repeat it.
- Separate format/lint/test processes advertised as parallel competed for one worktree lock.
- The `--non-browser` test option included marketing browser tests but omitted app component tests and repository scripts. Its name did not describe its coverage.
- Ordinary docs builds fetched a moving Nix configuration and rewrote tracked source. A clean candidate could change during verification without an authored edit.
- Component-browser isolation repeated translation compilation in every process. Listing the same 316 browser files took 21.46 seconds normally and 1.08 seconds with precompiled translations. Each shard now generates translations once before discovery and all isolated processes; the tests and their isolation remain intact.
- The separately measured existing test subset passed in 174.61 seconds. Backend tests took 66.80 seconds; frontend server tests took 174.07 seconds including preparation, with 1,970 tests across 383 files. This is not full browser, race, integration or production-build coverage.

The misleading earlier 10m32s figure measured only the final tag-to-deployment interval for v7.31.1. It excluded the preceding preparation, failed setup, cancellations and recovery. The agent process also contributed: it proceeded through remote retries before establishing a reliable local admission command. A faster final attempt did not repair that feedback loop.

## Decisions for OpenPost

1. Run the maintained local verification tasks before the first candidate push. Bind the push and tag to the checked clean revision and reject changes during checks. Keep failure reproduction local.
2. Make tag validation independent of cancellation of a moving main run. Reuse a completed exact-SHA proof when available; otherwise retain all remote gates. Existing immutable tags resume without pulling unrelated commits into the candidate.
3. Give setup its own short deadlines. Verify runner capabilities before reusing installed tools, and preserve pinned browser versions. Report actual canceled steps and GitHub timeout annotations rather than guessing why a run stopped.
4. Keep expensive production regressions, but run them once per validation plan and cache them using declared source, tool, configuration and dependency inputs. A result cache is an optimization, not evidence that a different revision was tested.
5. Use the committed external documentation snapshot during builds. Make upstream refresh explicit and reviewable.
6. Report preparation, remote validation/publication and live deployment distinctly. Keep full E2E, race, Hosted integration, security and platform build requirements visible. Do not use short Postiz runs or selected upstream suites to justify dropping them.

Further optimization should follow measured bottlenecks: dependency-aware local selection, duration-balanced test shards, reliable CI result caches, and reducing duplicate main/tag work when no completed proof exists. Each needs a complete input/dependency model and an explicit acceptance test. The current repair does not claim that full cold validation, all platforms and deployment fit five minutes. See [the operating workflow](../development/releases.md).
