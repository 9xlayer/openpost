# Beeper transport source investigation

Reviewed: 2026-10-20. Scope: how Beeper-associated public bridge code receives, reconciles, and sends messages for networks that overlap OpenPost, and what its design teaches us about an active mobile chat experience. This is source research, not a production implementation or a test of a signed-in Beeper account.

## Findings

Beeper's chat experience does not come from one universal WebSocket. It combines provider-specific live connections or frequent incremental polling, stored conversation state, explicit reconnection and catch-up, and send/echo reconciliation. Its present cloud and on-device connection modes also differ substantially. The useful architectural lesson is to separate fast local display, provider ingestion, catch-up, and background notification delivery.

The public code establishes concrete mechanisms. It does **not** establish which exact public commit is currently running inside every Beeper release or backend deployment. Beeper's organization page links Meta, Twitter, and LinkedIn to these repositories; Bluesky has a public mautrix bridge but is absent from the current Beeper help connection-type list. Do not convert the existence of that bridge into a claim that Bluesky is generally available in shipped Beeper mobile. [Beeper's source index](https://github.com/beeper), [current connection types](https://help.beeper.com/chat-networks/using-on-device-chat-network-connections-in-beeper).

| Network            | Mechanism in pinned public source                                                                                                                 | Authentication/session boundary                                                                            | Relevant lesson for OpenPost                                                                    |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Facebook Messenger | Persistent DGW/Lightspeed WebSocket; WhatsApp-derived client for encrypted Messenger threads                                                      | User-session cookies/native session and device keys, rather than OpenPost's Facebook Page OAuth connection | Streaming plus catch-up, but not a drop-in transport for Page messaging                         |
| Instagram          | Dedicated Instagram connector in the Meta repository; DGW/Lightspeed stream, WebSocket for web-cookie sessions or HTTP stream for native sessions | Instagram user session, cookies or native mobile session                                                   | Persist provider sequence, process deltas, rebuild snapshot when required                       |
| X                  | XChat WebSocket plus 10-second REST polling primarily for untrusted/message-request conversations                                                 | User session/cookies, XChat token and encryption keys                                                      | Live and polling paths can coexist; viewing a conversation explicitly triggers priority refresh |

| LinkedIn           | Authenticated Voyager `text/event-stream`, with heartbeat and token-based resync                                                                  | LinkedIn user cookies/browser session                                                                      | Stream reconnect must reconcile missed changes                                                  |
| Mastodon           | No applicable Beeper connector established                                                                                                        | Beeper help explicitly says Fediverse apps are unsupported                                                 | Investigate Mastodon's official streaming API directly, not a supposed Beeper implementation    |

Every transport claim above has pinned source evidence below. The official-provider API choice and feasibility for OpenPost require the companion OpenPost/provider investigation. The private session transports here must not be treated as official business OAuth APIs.

## Messenger: current source is newer than old MQTT explanations

The current `messagix.NewClient` creates a DGW socket using `dgw_lightspeed` as its WebSocket URL, session cookies, a browser origin, and an on-connect callback. The shared socket actually dials with `websocket.Dial` when no native HTTP stream is configured. Describing this current implementation as simply MQTT would be inaccurate, even though an older MQTT log string remains in the connector. [Client construction](https://github.com/mautrix/meta/blob/c4099692425e85b167adb76954c78baea201af89/pkg/messagix/client.go#L74-L109), [socket implementation](https://github.com/mautrix/meta/blob/c4099692425e85b167adb76954c78baea201af89/pkg/messagix/dgw/socket.go#L204-L233).

On connection it loads/fetches thread state and ensures required Lightspeed sync groups are synchronized before announcing `ConnectedEvent` or `ReconnectedEvent`. It has sync-group cursors and a cached reconnection state. The connector only saves reconnection state after its initial table and outstanding tables have been handled. This is a useful rule: the recovery checkpoint must describe applied state, not merely bytes received. [On-connect sync](https://github.com/mautrix/meta/blob/c4099692425e85b167adb76954c78baea201af89/pkg/messagix/socket.go#L50-L74), [state-save guard](https://github.com/mautrix/meta/blob/c4099692425e85b167adb76954c78baea201af89/pkg/connector/client.go#L548-L587).

Encrypted Messenger is a second protocol path. `MetaClient` owns a `whatsmeow.Client` and device store; encrypted sends call `SendFBMessage` with an authored/generated message ID. Plain sends create an offline threading ID, submit tasks, and map the optimistic ID to the returned remote message ID. The reply should appear once despite arriving through both the send response and the live connection. [Client fields](https://github.com/mautrix/meta/blob/c4099692425e85b167adb76954c78baea201af89/pkg/connector/client.go#L33-L83), [send routing and optimistic-ID resolution](https://github.com/mautrix/meta/blob/c4099692425e85b167adb76954c78baea201af89/pkg/connector/handlematrix.go#L59-L190).

This is a personal Messenger session architecture with device registration/encryption concerns. It is not evidence that OpenPost can use this connection for an existing Facebook Page OAuth grant. The transferable part is recovery and correlation, not credential extraction or replacing the business provider adapter.

## Instagram: separate connector, sequence-aware live deltas

The current repository contains two different bridges. `mautrix-meta` is Messenger; `mautrix-instagram` uses its own `igconnector` and `instameow`. The old Python `mautrix/instagram` and `mautrix/facebook` histories are not the right implementation baseline. The current Meta README explicitly describes the split. [Pinned README](https://github.com/mautrix/meta/blob/c4099692425e85b167adb76954c78baea201af89/README.md#L1-L7).

`instameow` establishes a persistent DGW stream with a provider sequence cursor. Web sessions use a WebSocket; mobile/native sessions select the HTTP streaming implementation with native session headers. This is still an unofficial user-session protocol, even when an internal header is named `OAuth`. It is not Meta's public OAuth business messaging API. [Socket options and native branch](https://github.com/mautrix/meta/blob/c4099692425e85b167adb76954c78baea201af89/pkg/instameow/socket.go#L148-L192), [native auth headers](https://github.com/mautrix/meta/blob/c4099692425e85b167adb76954c78baea201af89/pkg/instameow/native_socket.go#L18-L43).

The stream init includes the last applied `seq_id`, snapshot timestamp and retry count. Incoming delta events are passed to the event handler before sequence advancement. A `SeqIDUpdate` persists progress. A provider `Resnapshot` event explicitly invalidates the cursor and requests a new snapshot. Reconnection is immediate after a previously established connection drops; consecutive connection failures use exponential delay capped at 60 seconds. [Reconnect loop](https://github.com/mautrix/meta/blob/c4099692425e85b167adb76954c78baea201af89/pkg/instameow/socket.go#L55-L131), [cursor and delta processing](https://github.com/mautrix/meta/blob/c4099692425e85b167adb76954c78baea201af89/pkg/instameow/socket.go#L216-L344), [saved sequence and resnapshot handling](https://github.com/mautrix/meta/blob/c4099692425e85b167adb76954c78baea201af89/pkg/igconnector/handlemeta.go#L149-L175).

The connector loads its saved sequence at startup. Initial mailbox processing separately pages thread history if the first page fails to cover activity since the previous sequence timestamp. This is a distinct reconciliation job, not merely reconnecting a socket and hoping no events were lost. [Startup](https://github.com/mautrix/meta/blob/c4099692425e85b167adb76954c78baea201af89/pkg/igconnector/client.go#L153-L181), [mailbox and backfill](https://github.com/mautrix/meta/blob/c4099692425e85b167adb76954c78baea201af89/pkg/igconnector/chatsync.go#L36-L101).

Sends carry an offline threading ID and use the response's message ID/timestamp for the canonical stored message. Incoming messages carry that same canonical remote message ID into the framework. The connector's optional incoming transaction-ID field is commented out, so do not claim that every Instagram path currently correlates by client transaction ID. The central framework still checks stored remote IDs for duplicates. [Send](https://github.com/mautrix/meta/blob/c4099692425e85b167adb76954c78baea201af89/pkg/igconnector/handlematrix.go#L134-L193), [incoming message](https://github.com/mautrix/meta/blob/c4099692425e85b167adb76954c78baea201af89/pkg/igconnector/handlemeta.go#L396-L413).

## X: streaming plus active-conversation-aware polling

The bridge's XChat path opens a persistent WebSocket after inbox import. It also runs REST polling, primarily to cover untrusted/message-request conversations that do not receive XChat live updates. These paths are coordinated rather than blindly rendered as independent messages. [Connector startup](https://github.com/mautrix/twitter/blob/8fe76fcb254e42f8d631b4d5fcff11c85552fcb2/pkg/connector/client.go#L433-L468), [polling purpose](https://github.com/mautrix/twitter/blob/8fe76fcb254e42f8d631b4d5fcff11c85552fcb2/pkg/twittermeow/polling.go#L16-L28).

**A concrete UX hook exists:** `HandleMatrixViewingChat` calls `SetActiveConversation`. That immediately short-circuits the polling timer, and subsequent polls alternate inclusion of `ActiveConversationID`. The ordinary poll interval is 10 seconds. Authentication failure stops polling; other failures back off, with additional treatment for rate limits. The cursor changes only after the returned events have been handled successfully. This is the clearest source-backed precedent for telling the server which chat the user is actively viewing. [Viewing hook](https://github.com/mautrix/twitter/blob/8fe76fcb254e42f8d631b4d5fcff11c85552fcb2/pkg/connector/handlematrix.go#L883-L890), [polling implementation](https://github.com/mautrix/twitter/blob/8fe76fcb254e42f8d631b4d5fcff11c85552fcb2/pkg/twittermeow/polling.go#L55-L171).

The socket starts with a one-second retry delay, doubles toward a five-minute cap, pings every 30 seconds and gives pings a 10-second timeout. Backoff resets after a stable connection, not simply a successful handshake. On reconnect it runs a handoff catch-up before considering the socket ready. This prevents a gap between a prior inbox fetch and the newly attached live stream. [Connection constants](https://github.com/mautrix/twitter/blob/8fe76fcb254e42f8d631b4d5fcff11c85552fcb2/pkg/twittermeow/websocket.go#L22-L31), [catch-up and readiness](https://github.com/mautrix/twitter/blob/8fe76fcb254e42f8d631b4d5fcff11c85552fcb2/pkg/twittermeow/websocket.go#L170-L208).

Saved state includes continuation cursor, maximum user sequence and message pull version. Failed-event persistence blocks progress past unresolved event failures. Checkpoint-save errors roll in-memory metadata back to the preceding state. These are correctness features a production chat collector needs alongside low latency. [Checkpoint and failures](https://github.com/mautrix/twitter/blob/8fe76fcb254e42f8d631b4d5fcff11c85552fcb2/pkg/connector/client.go#L605-L676).

Sending uses a client message ID and registers an expected remote echo before dispatch. The mutation response is decoded to get the canonical XChat sequence ID, and the later echo updates existing metadata instead of creating another visible message. The framework separately distinguishes no-ack and no-echo timeout states. These mechanisms improve reconciliation; they do not prove exactly-once remote delivery after every ambiguous timeout. [XChat send](https://github.com/mautrix/twitter/blob/8fe76fcb254e42f8d631b4d5fcff11c85552fcb2/pkg/connector/handlematrix.go#L305-L381), [existing-echo behavior](https://github.com/mautrix/twitter/blob/8fe76fcb254e42f8d631b4d5fcff11c85552fcb2/pkg/connector/handletwit.go#L335-L355), [framework timeout distinction](https://github.com/mautrix/go/blob/dd2efd475311d773fab447f416357fcadf14bdb1/bridgev2/portal.go#L1592-L1617).

Authentication includes password/browser-assisted and cookie login, plus XChat encryption key recovery/PIN flows. This is not the same as OpenPost's public X v2 OAuth token. [Login implementation](https://github.com/mautrix/twitter/blob/8fe76fcb254e42f8d631b4d5fcff11c85552fcb2/pkg/connector/login.go#L44-L151).

The current official X Activity API separately documents persistent HTTP streams or webhooks, including private OAuth 2.0 `dm.received`, `dm.sent`, `dm.read`, and `dm.indicate_typing` events. It also distinguishes encrypted `chat.*` events from legacy unencrypted DMs. Thus, do not conclude that OpenPost must reproduce the Beeper session transport to obtain official real-time X DM events. App entitlement, payload availability, token migration and cost remain separate implementation checks. [Official X Activity API](https://docs.x.com/x-api/activity/introduction).

## Bluesky: a useful example of chat without a streaming API

This bridge uses `chat.bsky.convo.getLog` every five seconds with a persisted account cursor. Requests go through the user's PDS with the `Atproto-Proxy` header selecting `did:web:api.bsky.chat#bsky_chat`. JWTs are refreshed before expiry. This is the public chat protocol rather than a private web-session implementation. [Clients and proxy](https://github.com/mautrix/bluesky/blob/0c2076b1b0093ed3c131520f1fd032c3898414ef/pkg/connector/client.go#L39-L62), [poll interval and log cursor](https://github.com/mautrix/bluesky/blob/0c2076b1b0093ed3c131520f1fd032c3898414ef/pkg/connector/client.go#L154-L267).

This avoids reading every message page of every conversation on each tick. `getLog` returns incremental account events, which the connector normalizes into bridge events. A send uses `sendMessage` and stores the response's remote ID/timestamp. That same ID appears in incoming log events and is available for deduplication. [Incoming](https://github.com/mautrix/bluesky/blob/0c2076b1b0093ed3c131520f1fd032c3898414ef/pkg/connector/handlebsky.go#L32-L72), [outgoing](https://github.com/mautrix/bluesky/blob/0c2076b1b0093ed3c131520f1fd032c3898414ef/pkg/connector/handlematrix.go#L37-L74).

Do not copy its incomplete reliability details wholesale. The reviewed source explicitly has TODOs for inbox pagination and polling backoff. Initial inbox fetch is limited to 20 chats, the event switch only handles message creation, and `pollOnce` advances its cursor without receiving a success result from `HandleEvent`. A production OpenPost implementation must process all relevant event kinds, guarantee durable progress before checkpointing, page correctly, and respect rate-limit backoff. [Initial list limit](https://github.com/mautrix/bluesky/blob/0c2076b1b0093ed3c131520f1fd032c3898414ef/pkg/connector/client.go#L165-L171), [polling weaknesses](https://github.com/mautrix/bluesky/blob/0c2076b1b0093ed3c131520f1fd032c3898414ef/pkg/connector/client.go#L214-L267), [event coverage](https://github.com/mautrix/bluesky/blob/0c2076b1b0093ed3c131520f1fd032c3898414ef/pkg/connector/handlebsky.go#L32-L40).

Five-second polling implies about 720 requests per hour or 17,280 per day for each continuously connected account, before additional requests. That arithmetic is not a provider allowance or a recommendation to poll every idle Hosted account forever. Active foreground sessions should receive a separate, bounded freshness policy. An ideal five-second periodic poll adds zero to five seconds of detection delay before network and application processing; it is not instant delivery.

## LinkedIn: live personal messaging is not public marketing API access

Beeper names LinkedIn as both an on-device and a Cloud connection. The current public Go bridge supports cookie and email/password login. It uses authenticated browser-session requests with CSRF and Voyager-specific headers. [Beeper connection types](https://help.beeper.com/chat-networks/using-on-device-chat-network-connections-in-beeper), [login](https://github.com/mautrix/linkedin/blob/ad282448fee3472678394f9a5478f2696fa011ca/pkg/connector/login.go#L34-L110).

The real-time path performs an HTTP GET accepting `text/event-stream` and reads `data:` JSON lines. A companion loop sends a heartbeat every minute. Retry delay grows linearly to a one-minute cap, with a maximum attempt count and distinct credential/transient error states. On a changed server session it resyncs conversations; otherwise it retrieves changes using a saved conversation sync token. [Live connection](https://github.com/mautrix/linkedin/blob/ad282448fee3472678394f9a5478f2696fa011ca/pkg/linkedingo/realtime.go#L97-L264), [session and sync-token handling](https://github.com/mautrix/linkedin/blob/ad282448fee3472678394f9a5478f2696fa011ca/pkg/connector/client.go#L88-L125).

Outgoing messages forward the input transaction ID, or generate a UUID, and store the remote message ID from the response. Incoming events and backfill therefore share a canonical identity. This demonstrates an engineering pattern, not permission or an official public API for OpenPost to expose LinkedIn personal DMs. [Send result and transaction](https://github.com/mautrix/linkedin/blob/ad282448fee3472678394f9a5478f2696fa011ca/pkg/connector/handlematrix.go#L210-L228).

## Mastodon: no Beeper implementation to inspect

The reviewed Beeper help page explicitly says Mastodon, Pleroma and Pixelfed are unsupported. The source index does not establish a maintained first-party Beeper Mastodon chat bridge. Do not infer a proprietary hidden transport from this absence, and do not use Bluesky bridge code as Mastodon evidence. OpenPost should investigate its official Mastodon APIs directly. ## Cloud, on-device, mobile backgrounding

Beeper's current help distinguishes direct per-device connections from cloud-hosted connections. Direct sessions require setup on each device; Cloud connections synchronize through Beeper's servers. Several overlapping networks offer both. A per-provider public bridge repository does not show the complete shipped mobile runtime or prove that a particular account is using its Cloud path. [Beeper connection types](https://help.beeper.com/chat-networks/using-on-device-chat-network-connections-in-beeper).

Beeper's iOS engineering explanation distinguishes foreground sync from background notifications. For Cloud connections its backend receives messages and sends pushes; iOS uses a Notification Service Extension to process/decrypt notifications. For on-device connections Beeper registers for the network's native push mechanism, forwards an encrypted wake-up payload, and lets the extension fetch/process what is needed. Shared storage requires coordination between the app and extension. This is an advanced native integration, not an indefinitely running mobile WebSocket. [Beeper iOS notifications, 2025-10-01](https://blog.beeper.com/2025/10/01/how-beeper-ios-implements-notifications/).

Inference for OpenPost: its existing server-authorized provider architecture fits server ingestion plus an app-facing event stream and conventional APNs/FCM wake-ups. Reproducing Beeper's private on-device provider sessions and push registrations would be a different product architecture. Foreground live updates and background notification delivery need separate implementations and acceptance criteria.

## Framework mechanisms worth learning from

The shared framework normalizes provider events into per-conversation processing. Before rendering an incoming message it checks pending sends and stored remote message IDs, so live events and backfill can converge. It explicitly supports responses where the send knows the remote message ID immediately and responses that remain pending until a later echo supplies it. [Remote deduplication](https://github.com/mautrix/go/blob/dd2efd475311d773fab447f416357fcadf14bdb1/bridgev2/portal.go#L3226-L3256), [pending-send contracts](https://github.com/mautrix/go/blob/dd2efd475311d773fab447f416357fcadf14bdb1/bridgev2/portal.go#L1494-L1545).

The existence of a method named `QueueRemoteEvent` does not prove the queue is durable across process death. Source shows portal event queues and pending-send maps in memory. OpenPost's own durable database-job invariant should remain authoritative. Ingest an event durably before advancing its provider cursor, make upserts idempotent, and send app notifications only after commit. [Queue entry](https://github.com/mautrix/go/blob/dd2efd475311d773fab447f416357fcadf14bdb1/bridgev2/queue.go#L230-L275), [portal queue](https://github.com/mautrix/go/blob/dd2efd475311d773fab447f416357fcadf14bdb1/bridgev2/portal.go#L357-L404).

## Recommended transfer into OpenPost

These are recommendations, not existing OpenPost capabilities verified by this sub-investigation:

1. Keep official provider authorization. Use webhooks/streams where the existing grant and public provider APIs allow them; use incremental account logs or bounded delta polling elsewhere.
2. Add a short-lived active-inbox/active-conversation lease. Opening a chat requests immediate catch-up; heartbeat renewals keep only that actor's relevant account/conversation hot; background/expiry stops elevated polling. Deduplicate provider work across devices and Workspace members. The X bridge's viewing hook is direct precedent.
3. Keep foreground freshness and cold history independent. New-message ingestion should not wait behind a full historical thread sweep. Reconnect from saved high-water marks and repair gaps before reporting current state.
4. Give web and mobile a common server-owned committed-event cursor. Stream committed changes, resume after reconnect, and fall back to a snapshot when retention is exceeded. The app must not mistake a healthy app-server socket for a healthy provider connection.
5. Treat send state as a durable lifecycle. Preserve a client request ID, show the local bubble immediately, distinguish queued/sending/sent/unknown/failed, reconcile a later remote echo into that bubble, and never automatically resend an ambiguous outcome without a provider-safe strategy.
6. Use native background push to alert and wake the app; refresh on resume. Do not promise permanent mobile socket execution or exactly-once push delivery.
7. Show provider truth briefly: connecting, live/current, last checked, delayed, reconnect required. Use read receipts or delivered status only when the provider supplies them. A fast animation is not evidence of remote delivery.
