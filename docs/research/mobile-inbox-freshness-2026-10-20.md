# Mobile Inbox freshness: Beeper lessons and an OpenPost design

Reviewed 20 October 2026. Research and proposed implementation, not a shipped change. The user wants existing DMs to behave like a chat app while actively sending and receiving, alongside public comment replies.

**Yes, OpenPost can support a much more responsive chat loop.** It needs both provider-to-server ingestion and server-to-client updates. Changing the current 15-minute collector interval, or adding a WebSocket only between mobile and OpenPost, solves only part of the problem. The recommended design uses official provider events, incremental polling where necessary, durable recovery, and activity-aware collection shared across devices.

Read the companion [Beeper bridge source audit](./beeper-bridge-transports-2026-10-20.md) for the pinned bridge revisions, exact functions, auth models, licenses, and a 23-record source ledger. Public bridge HEAD is evidence about that code, not proof of the exact implementation in every current Beeper app or Cloud deployment. Its Bluesky bridge exists publicly but current Beeper help does not establish general shipped mobile Bluesky availability.

## What Beeper teaches us

Beeper-associated source uses provider-specific live transports rather than a single universal protocol. Current Meta source separates Messenger and Instagram: Messenger uses DGW/Lightspeed WebSocket and an encrypted Messenger client, while Instagram selects WebSocket or native HTTP streaming. X combines XChat streaming with polling for additional coverage. LinkedIn uses a private browser-session event stream. These authenticate personal user sessions, not OpenPost's existing business OAuth grants. The companion audit links the exact implementation evidence.

The more transferable mechanisms are:

- **Viewing a chat changes collection priority.** The X bridge's viewing hook short-circuits a poll immediately and makes subsequent collection aware of the active conversation.
- **Catch-up and live traffic meet at one identity.** A send response, incoming echo and historical fetch reconcile to one remote message instead of producing duplicate bubbles.
- **Connection readiness includes recovery.** A successful socket handshake alone does not mean missed messages have been applied. Cursors and sequence checkpoints need to describe processed state.
- **Incremental polling can feel like chat.** The public Bluesky bridge polls the official account event log every five seconds, rather than fetching every conversation's history repeatedly.
- **Foreground connections and background alerts are different systems.** Beeper's published iOS architecture uses push and a Notification Service Extension for background work. It does not depend on an indefinitely running app socket. See [Beeper's iOS engineering explanation](https://blog.beeper.com/2025/10/01/how-beeper-ios-implements-notifications/).

Do not copy the bridge implementations wholesale. The bridge repositories have AGPL licenses and specific embedding exceptions; those exceptions do not automatically apply to OpenPost. The source audit records the actual license files. This proposal adopts independently implemented behavior through OpenPost's existing owners.

### Meta: the official event route exists

Meta's own [Instagram sample](https://github.com/fbsamples/original-coast-clothing-ig/blob/d68684226a2db3d4830e0a0771a1abd5c0dc635b/README.md#L160-L170) documents subscribing to message and comment webhooks. Its [handler](https://github.com/fbsamples/original-coast-clothing-ig/blob/d68684226a2db3d4830e0a0771a1abd5c0dc635b/app.js#L83-L149) processes Instagram message events and distinguishes message echoes. The official [Messenger sample](https://github.com/fbsamples/messenger-platform-samples/blob/3c3853a84a5d87d2567e75e649655822f535fdf6/quick-start/app.js) demonstrates a Page webhook receiver.

These are evidence for event ingestion, not current approval or complete current authentication instructions. The older Instagram sample requires a linked Facebook Page; OpenPost also supports direct Instagram Login. The current Meta developer-document pages returned internal errors in this research session, and Postman returned an application shell. Exact current subscription payloads, signature requirements, app-review status and both Instagram login modes must be verified against current Meta documentation and an authorized test installation during implementation. Do not copy the samples' old signature handling or their asynchronous acknowledgement behavior into production.

Proposed processing: verify the raw callback signature with the owning installation's secret, resolve the receiving account through stored app/account bindings, normalize supported fields, persist an idempotent receipt, then acknowledge. Queue provider hydration only when the event lacks data needed for the supported message view. Avoid one full-account refresh per message. Outbound echoes belong in send reconciliation, not the unread incoming count. Keep reply-window enforcement server-side.

### Bluesky: the strongest immediate improvement

The official Bluesky app corroborates activity-aware incremental polling. At source revision `ae153086a76a6df86e6af2c0c0070977c44e7f0b`, [conversation constants](https://github.com/bluesky-social/social-app/blob/ae153086a76a6df86e6af2c0c0070977c44e7f0b/src/state/messages/convo/const.ts#L1-L4) specify 4 seconds active, 30 seconds on the message screen and 60 seconds for an inactive conversation. [Event-bus defaults](https://github.com/bluesky-social/social-app/blob/ae153086a76a6df86e6af2c0c0070977c44e7f0b/src/state/messages/events/const.ts) are 60 seconds normally and 5 minutes backgrounded. The [event bus](https://github.com/bluesky-social/social-app/blob/ae153086a76a6df86e6af2c0c0070977c44e7f0b/src/state/messages/events/agent.ts#L313-L430) chooses the fastest active request, prevents overlapping polls and reads the account log from its revision cursor. Its [resume logic](https://github.com/bluesky-social/social-app/blob/ae153086a76a6df86e6af2c0c0070977c44e7f0b/src/state/messages/events/agent.ts#L240-L263) preserves an existing cursor after failure instead of jumping to a new head and skipping events.

The official [getLog lexicon](https://github.com/bluesky-social/social-app/blob/ae153086a76a6df86e6af2c0c0070977c44e7f0b/lexicons/chat/bsky/convo/getLog.json) includes create/delete/read and reaction events, plus conversation membership and state changes. A public post firehose is not the private DM log. Unknown event kinds must not crash ingestion or silently erase supported content.

OpenPost can reuse its chat service routing and token owner while replacing the expensive live collection shape. Today a full 100-conversation page can require 101 provider requests: one list call plus 100 history calls. Running that same code every five seconds could require 1,212 requests per minute, before backfill. One incremental account-log request per five-second tick is about 12 requests per minute before hydration, pagination and recovery. This is arithmetic from the current code, not a load benchmark or a provider allowance. Do not multiply polling by the number of viewers, and do not poll every idle account forever at the active rate.

Cold conversation discovery and earlier message history remain separate paginated operations. Save the event cursor only after the corresponding messages, tombstones, read-state changes and app-facing change records commit. Bootstrap with a known revision, hydrate an inbox snapshot, replay changes from that revision, then enter active polling, so initialization has no snapshot-to-live gap. Bounded pagination/reconciliation repairs expired cursors.

### Mastodon: an official stream, not a Beeper bridge

Mastodon's [streaming API](https://docs.joinmastodon.org/methods/streaming/) documents authenticated HTTP event streams or WebSocket, the `direct` stream and `conversation` events. Discover the streaming hostname through instance metadata rather than assuming the REST hostname. A conversation update can trigger a bounded targeted read when it does not contain everything needed for the view. Reconnect with jitter and repair missed history through REST; a successful connection is not a gap-free replay guarantee.

Use a dedicated streaming transport with cancellation, bounded handshake/headers and idle-health detection. OpenPost's ordinary provider HTTP client has a 30-second whole-request timeout and buffered-body helper, so it must not be used unchanged for an indefinite stream. Keep discovered hosts behind the existing network/redirect guard and keep credentials out of URLs and logs. Direct-visibility statuses must remain separate from public engagement and retain their actual privacy meaning.

### X: current official events materially change the answer

The current [X Activity API](https://docs.x.com/x-api/activity/introduction) documents webhook or persistent HTTP delivery for private `dm.received`, `dm.sent`, read and typing events. Private subscriptions require the user's OAuth 2.0 authorization. OpenPost's adapter currently declares an OAuth 1.0 grant, so existing tokens do not satisfy that requirement automatically. Preserve working publishing connections and add an explicitly account-resolved messaging authorization path; do not replace every token or capability implicitly. The old [Account Activity page](https://docs.x.com/x-api/account-activity/introduction) is marked deprecated in favor of XAA.

The [payload reference](https://docs.x.com/x-api/activity/event-payloads) distinguishes legacy DM plaintext from XChat's encoded encrypted payloads. Receiving `chat.received` does not give OpenPost an established decryption or encrypted-send implementation. For legacy DMs, the documented event carries message identity, sender/recipient and body, allowing ingestion without polling every minute. Persist `event_uuid` for receipt deduplication and canonical message IDs for model reconciliation.

[Current event pricing](https://docs.x.com/x-api/activity/event-pricing) lists inbound `dm.received` and `chat.received` at USD 0.01 per event on pay-per-use; sent/read/typing events are listed as not billed. Ten thousand inbound events would therefore be USD 100 before other usage. This calculation is not a spending authorization or a verified OpenPost invoice. Extend the existing provider-cost admission/accounting owner before provisioning subscriptions, and verify current billing semantics and entitlement with the installation.

The [current rate-limit table](https://docs.x.com/x-api/fundamentals/rate-limits) lists DM lookup at 15 requests per 15 minutes per user, and DM sends at 15 per 15 minutes per user with additional daily limits. A five-second lookup loop would request 180 calls per 15 minutes. Even successful event ingestion does not remove send limits. Treat actual response headers and installation access as authoritative, reserve recovery/read/write budget and expose delayed/throttled behavior. Never market unrestricted messenger parity from event support alone.

X's [webhook documentation](https://docs.x.com/x-api/webhooks/introduction) describes HTTPS reachability, fast acknowledgement, challenge-response and raw-body signature checks. Its exact callback/auth setup and replay entitlement need an implementation probe. Prefer webhook delivery for the Hosted path because it avoids consuming scarce application stream connections per account; support a supervised shared upstream connection only where the installation requires it. This is a design choice, not a measured superiority claim.

The echo interleaving is a source-identified risk with a small schema probe, not a reproduced live incident. In an in-memory SQLite database using the production remote-ID unique-index shape: insert a queued local row with empty remote ID; insert the incoming echo row with remote ID `remote-42`; assign that ID to the queued row. SQLite returns `UNIQUE constraint failed: direct_messages.conversation_id, direct_messages.remote_message_id`; the local row remains queued and the echo remains sent. This proves the schema collision for that interleaving, not its production frequency or a complete Go-service reproduction. Turn it into an actual service-boundary failing regression during implementation.

## Proposed architecture

### Keep provider ingestion on the server

Maintain one collection owner per provider installation/account, shared by web and mobile users. Provider credentials stay in the existing token/grant boundary. Mobile supplies viewing activity, not a provider login session. Support three transport capabilities behind the messaging owner: verified webhook events, supervised streams, and incremental pull. Do not make the existing `FetchMessages` API pretend that an older-history pagination cursor is a live event checkpoint.

Normalize events into one durable apply path: authorize the account binding, deduplicate the event, reconcile message identity, update message/conversation/read state, append an app-facing change, and commit the matching provider checkpoint. Acknowledge a webhook only after durable receipt. For multi-page pulls either apply/checkpoint each safe page or durably stage pending work; never advance past an unapplied event. Emit notifications after commit through the existing notification owner. Do not store entire raw provider payloads as a generic event archive; retain only normalized permitted fields and bounded receipts under provider deletion/retention rules.

Long-lived Mastodon/X connections belong to a supervised worker component with a durable lease, lease fencing, checkpoint and restart/reconnect behavior. Do not occupy the generic serial job runner forever or launch untracked goroutines from HTTP requests. Short incremental polls can remain bounded durable jobs with due timestamps and a per-account coalescing identity. Preserve SQLite self-hosting and PostgreSQL Hosted behavior without requiring Redis or another queue.

### Add a short-lived viewing lease

Proposed interface: the authenticated client reports `workspace_id`, optional conversation, view kind and a short-lived session identity; the server resolves account IDs and capabilities. Example policy: renew about every 20 seconds, expire after 60 seconds, release best-effort on background or navigation. Expiry is authoritative because mobile apps are suspended or killed. Aggregate the strongest valid lease across devices/members so two viewers do not double provider traffic. Limit account fan-out, concurrent hot accounts and history work per actor/Workspace.

Opening a chat requests a coalesced immediate catch-up. Bluesky's proposed active interval starts at 4–5 seconds, then slows toward 30–60 seconds in the inbox and cold cadence when nobody is looking. These are initial tuning values, subject to provider budgets and measurement. Webhook platforms retain their subscription independent of mobile activity; viewing a chat does not create and delete subscriptions repeatedly. X REST fallback follows its actual quota rather than the Bluesky timer. Leases never bypass opt-in, account state, roles or rate-limit backoff.

### Deliver committed changes to both clients

Recommend a small inbox-specific durable change journal and an authenticated cursor endpoint first. One bounded HTTP long poll per foreground client, for example up to 25 seconds, works with the existing native HTTP transport without adopting provider sockets in mobile. The endpoint returns immediately when committed changes exist, not only when the wait expires. Reuse the same cursor protocol if SSE or WebSocket later becomes useful; prove native streaming and proxy behavior before choosing that delivery mechanism. Websocket is an implementation option, not the requirement.

Changes contain minimal typed identifiers/revisions or bounded authorized projections: message added/updated/deleted, conversation changed, read/archive state, send outcome, collection health. Reconcile through `@openpost/query-catalog` keys and native/web adapters. Do not refetch every loaded conversation history on each event. Keep a snapshot/reset response for expired cursors and tombstones for deletions. A consistent snapshot/cursor boundary must prevent an event arriving during bootstrap from being missed. In PostgreSQL, a plain globally allocated sequence is not automatically commit ordered; serialize the relevant workspace revision under its transaction lock or use another proven commit-safe cursor scheme. Do not mark a cursor consumed before applying its changes.

Database state is authoritative across `web` and `worker` processes and multiple replicas. An in-memory notifier can reduce wait latency but is only a hint; periodic journal checks recover dropped wake-ups. Reauthorize each returned batch, bound concurrent waits and batch size, cancel on navigation/logout, respect session/Workspace changes and purge revoked cached content. Never carry bearer credentials in event-stream URLs.

### Treat sends as a reconciled lifecycle

1. Generate and persist a client operation ID before dispatch. Show a local Sending bubble immediately.
2. Server authorizes the stored destination and admits the operation transactionally. Scope idempotency to actor/server/Workspace/conversation and reject reuse with different content. Return the existing canonical row for a repeated identical operation.
3. Execute promptly through the existing durable write fence, with messaging work protected from slow history or generation jobs. HTTP admission means Queued, not Sent.
4. Apply the provider result and live echo through the same identity reconciliation. Either arrival order must converge; do not rely only on catching a unique-index error. Do not content-match identical messages, since people can legitimately send the same text twice.
5. Persist accepted, rejected, throttled and ambiguous states. An ambiguous provider acceptance remains explicit and must not cause blind retry. Terminal job failures/recovery must settle the visible message state. Native and web receive that state through the committed feed.

### Background delivery remains a separate slice

When the app backgrounds, release the active lease, stop foreground long polling and retain its cursor. Provider webhooks and server collectors continue under their configured cold/background policy. APNs/FCM can later alert the device through durable notifications with preview privacy, badge and thread-deep-link controls. On resume, catch up from the saved cursor and reestablish activity. Push is a wake-up hint, not the canonical message database or a guarantee that the OS runs app code immediately. The first in-app chat slice can ship without push, but it must not claim background messenger parity.

## Acceptance, measurements and rollout

Measure the segments separately: provider event time → server receipt; receipt → durable apply; commit → foreground screen; send tap → admission; admission → provider dispatch; provider acceptance → screen. A healthy mobile connection must not conceal a stale upstream collector. Proposed goals, not observed results: local bubble under 100 ms; committed update visible within 2 seconds under normal foreground conditions; active Bluesky incoming p95 below 10 seconds under supported budgets. Webhook provider-to-OpenPost latency and X's limits require separate real-account evidence. Record p50/p95/p99, provider error/backoff, queue wait, gap recovery, duplicate reconciliation and calls/cost per active account-hour.

Implement in this order:

1. **Message correctness and client delivery.** Scoped admission idempotency, both echo arrival orders, durable send-state projection, unread/archive behavior, a commit-safe journal and replay/reset endpoint. Add service-boundary regressions and cross-process proof. This improves web as well as enabling native.
2. **Bluesky active collection.** Separate log cursor/history cursor, cold bootstrap and gap repair, coalesced active leases, bounded rate-aware jobs, shared live updates. This is the strongest path to demonstrate a complete active chat without private transports or new paid subscriptions.
3. **Official Meta callbacks.** Installation-bound verification/subscriptions, idempotent event ingestion, outbound echoes, both Instagram login modes, scoped history recovery and an actual external-account round trip. App access remains a release gate.
4. **Mastodon streaming.** Leased stream ownership, safe hostname discovery, disconnect/backfill tests and bounded hydration. Verify on real supported instance variants.
5. **X messaging authorization and economics.** Verify XAA entitlement, OAuth 2.0 compatibility without breaking OAuth 1.0 publishing, private DM payloads, metering and send throttling. Keep encrypted XChat outside the legacy plaintext promise.
6. **Native delivery and optional push.** Keyboard/scroll anchors, identity-safe drafts, foreground/background handoff and privacy; later add tested APNs/FCM lifecycle. Reuse the original mobile Inbox UX spec in Vikunja task 694.

Release tests need duplicate/out-of-order callbacks; reconnect during a burst; event/receipt commit crash; cursor expiry; bootstrap race; echo-before-send-result and the reverse; lost HTTP admission response; two devices viewing one chat; expired activity leases; token refresh and revocation; opt-out during collection; inaccessible/deleted accounts; provider 429/402; worker crash and takeover; slow generic jobs; SQLite and PostgreSQL; phone process termination; network handoff; old-history paging while new traffic arrives. A fully replayed burst must produce the same permitted messages and unread state regardless of duplicate delivery. Exactly-once external sends cannot be promised when the provider supplies no safe reconciliation or idempotency mechanism.

Add new migrations at implementation time, not with guessed future numbers. Roll out behind provider-level ingestion/freshness flags, shadow normalized events before switching the authoritative path, and compare canonical IDs/counts rather than retaining raw payloads. A kill switch stops elevated polling/streams/subscriptions and leaves stored history and the old bounded recovery path usable. Do not enable a duplicate unfenced send path during rollout.
